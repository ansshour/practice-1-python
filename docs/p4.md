---
title: P4. Публикация на Helios
---

В задании P4 мы настроили обновление сайта на учебном сервере Helios ИТМО. Используем выданный учебный аккаунт, чтобы отработать загрузку файлов, публикацию и откат. Каждая сборка хранится отдельно: новую версию можно опубликовать, проверить и при необходимости заменить предыдущей.

[Открыть сайт на Helios](https://se.ifmo.ru/~s313344/) · [Открыть GitHub Pages](https://ansshour.github.io/practice-1-python/)

## Как обновляется сайт

После отправки изменений в репозиторий GitHub Actions собирает сайт с помощью MkDocs. Готовые файлы из `dist/` передаются на Helios по SSH с помощью rsync. Python на сервере не нужен: Helios раздаёт уже собранные страницы.

Новая сборка загружается в отдельный каталог. Пока идёт передача, посетитель видит действующую версию. После успешной загрузки ссылка `public_html` переключается на новый релиз, а предыдущая версия сохраняется для отката.

Если передача файлов не завершилась, переключения не будет. При ошибке, обнаруженной уже после публикации, откат нужно запустить вручную.

## Тестовые версии для веток

Основная ветка `main` обновляет сайт по адресу `https://se.ifmo.ru/~s313344/`. Для остальных веток создаётся preview — тестовая публикация по отдельной ссылке. По ней можно проверить изменения до включения в основной сайт.

Адрес preview привязан к имени ветки. Новые коммиты в этой ветке обновляют ту же тестовую публикацию. Для её появления не обязательно открывать pull request; автоматическую отправку ссылки комментарием в PR мы не настраивали.

Тестовые версии хранятся в общем каталоге preview. Обновление основного сайта не меняет их адреса.

## Проверка опубликованной версии

После публикации скрипт `healthcheck.sh` проверяет:

- сервер вернул HTTP 200;
- в `release.txt` записана ожидаемая версия;
- на странице `example/` есть контрольная строка `practice-1-site-ready`.

Проверка выполняется не более шести раз. Если все попытки неудачны, задание завершается ошибкой. Проверка сообщает о проблеме, но сама не откатывает сайт. Для возврата предыдущей версии предусмотрена ручная операция `rollback`, после которой выполняется та же проверка.

## Что показали испытания

Для сайта на MkDocs мы провели эксперимент в preview `mkdocs-check`:

| Действие | Результат |
| --- | --- |
| Опубликовали версию `v1` | По публичному адресу доступна первая версия |
| Опубликовали версию `v2` | Сайт обновился до второй версии |
| Прервали следующее обновление после загрузки, до переключения | Вторая версия осталась доступна; операция `interrupt` завершилась с кодом 42 |
| Запустили `rollback` | Сайт вернулся к первой версии |

После каждого этапа HTTP-проверки подтвердили ожидаемую версию. Эксперимент проверяет отказ до переключения и ручной откат. Потерю данных на сервере и длительную недоступность площадки мы не моделировали.

Отдельно измерили время работы тех же Bash-скриптов при локальном запуске через `/usr/bin/time -p`:

| Операция | Время |
| --- | ---: |
| Публикация второй готовой сборки с проверкой | 3,11 с |
| Откат с проверкой | 1,02 с |

Это единичные замеры для небольшого сайта. Установка зависимостей и сборка MkDocs в них не учитываются.

## GitHub Pages и Helios

| Критерий | GitHub Pages | Helios |
| --- | --- | --- |
| Публикация | Передаём готовую сборку сервису Pages | Передаём файлы по SSH/rsync и переключаем версию |
| Проверка | Логи Actions и HTTP-проверка сайта | Логи Actions, HTTP-проверка и просмотр каталогов по SSH |
| Возврат версии | Повторно публикуем нужный коммит | Переключаемся на сохранённую сборку |
| Если загрузка не завершилась | Публикацией артефакта управляет Pages | Новая сборка не становится действующей |
| Обслуживание | Веб-сервер обслуживает платформа | Сервер обслуживает ИТМО; в своём аккаунте мы следим за ключом доступа, местом на диске и сохранёнными релизами |

Для отката нужны две успешно опубликованные версии. Старые релизы автоматически не удаляются; правила их хранения и очистку ещё предстоит настроить.

## Настройка автоматизации

Файл [`.github/workflows/helios.yml`](https://github.com/ansshour/practice-1-python/blob/main/.github/workflows/helios.yml) запускается при push в любую ветку и вручную. Публикации выполняются по очереди: новый запуск не отменяет текущий.

| Ветка или операция | Что происходит |
| --- | --- |
| `main` | Сборка для `/~s313344/` и обновление основного сайта |
| Другая ветка | Сборка для `/~s313344/previews/branch-<хеш имени ветки>/` и обновление её preview |
| `workflow_dispatch`, `rollback` из `main` | Возврат предыдущей основной версии и проверка сайта |
| `workflow_dispatch`, `interrupt` | Намеренная остановка после загрузки, до переключения; задание завершается ошибкой |

Логику разделили между Bash-скриптами: `helios-ci.sh` готовит окружение CI, `helios-deploy.sh` загружает файлы, `helios-switch.sh` переключает релизы, `healthcheck.sh` проверяет сайт.

Сборки находятся в `.practice1/releases/<идентификатор>`. Идентификатор содержит SHA коммита, номер запуска и номер попытки. Для адреса preview используются первые 16 шестнадцатеричных символов SHA-256 имени ветки, поэтому само имя не попадает в команды SSH и пути. Ссылка на релиз переключается через `mv -fh`, а `lockf` не даёт выполнять переключения одновременно.

## Доступ к серверу

Параметры подключения `HELIOS_HOST`, `HELIOS_USER`, `HELIOS_PORT` и `HELIOS_URL` записаны в переменных окружения GitHub `helios`. Приватный ключ хранится в секрете `HELIOS_SSH_KEY`, проверенный ключ сервера — в `HELIOS_KNOWN_HOSTS`. SSH сверяет ключ сервера с сохранённым; временные файлы доступа удаляются в конце workflow.

Для публикации создан отдельный ключ. На Helios его права пока совпадают с правами учебного аккаунта: ограничение forced command не настроено. Ключ можно отозвать, удалив соответствующую публичную запись из `authorized_keys`.
