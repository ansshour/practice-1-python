## Адреса

- [Основной сайт на Helios](https://se.ifmo.ru/~s313344/).
- [GitHub Pages](https://ansshour.github.io/practice-1-python/) остаётся второй площадкой публикации.

## Схема доставки

MkDocs собирает сайт в GitHub Actions, затем каталог `dist/` передаётся по SSH/rsync на FreeBSD-сервер Helios. Управление доставкой написано на Bash: `helios-ci.sh` готовит CI, `helios-deploy.sh` загружает файлы, `helios-switch.sh` переключает релизы, `healthcheck.sh` проверяет опубликованный сайт через curl. Python на самом Helios не требуется: сервер раздаёт готовые статические файлы.

Каждый запуск получает отдельный каталог `.practice1/releases/<идентификатор>` в домашнем каталоге аккаунта. Публикация начинается только после успешной передачи файлов. `public_html` указывает на активную сборку; предыдущая ссылка сохраняется для отката. Переключение ссылки выполняется через `mv -fh`, с блокировкой `lockf` на сервере.

Каждая основная сборка содержит ссылку на общий каталог preview. Поэтому публикация основной версии не меняет адреса preview других веток.

## Workflow

Файл [`.github/workflows/helios.yml`](https://github.com/ansshour/practice-1-python/blob/main/.github/workflows/helios.yml) запускается при push в любую ветку и вручную. Запуски сериализованы группой `helios`; выполняющийся деплой не отменяется новым push.

| Ветка или операция | Поведение |
| --- | --- |
| `main` | Сборка для `/~s313344/`, публикация в корень |
| Другая ветка | Сборка для `/~s313344/previews/branch-<хеш имени ветки>/`, отдельная ссылка на релиз |
| `workflow_dispatch`, `rollback` из `main` | Переключение на предыдущую основную версию, затем healthcheck |
| `workflow_dispatch`, `interrupt` | Контролируемый отказ после загрузки, до переключения версии; job завершается ошибкой |

Для preview используется 16 шестнадцатеричных символов SHA-256 имени ветки. Это позволяет не помещать произвольное имя ветки в команды SSH и пути. Версия сборки содержит SHA коммита, номер запуска и номер попытки.

## Доступ и проверка результата

Ключ хранится в секрете `HELIOS_SSH_KEY` окружения `helios`, проверенный ключ сервера — в `HELIOS_KNOWN_HOSTS`. Передача приватного ключа в GitHub отдельно подтверждена владельцем. Содержимое секретов в репозиторий не записывается. SSH использует `StrictHostKeyChecking=yes`; временные файлы credentials удаляются в завершающем шаге workflow.

Параметры `HELIOS_HOST`, `HELIOS_USER`, `HELIOS_PORT`, `HELIOS_URL` находятся в переменных окружения GitHub. Это отдельный ключ, но на сервере он пока не ограничен forced command: он имеет права учебного аккаунта. При необходимости его можно отозвать, удалив соответствующий публичный ключ из `authorized_keys`.

Healthcheck проверяет HTTP 200, точное совпадение `release.txt` с ожидаемой версией и наличие `practice-1-site-ready` в HTML страницы `/example/`. Проверка повторяется до шести раз; несовпадение завершает job с ошибкой. Неудачный healthcheck сам по себе не откатывает сайт: оператор запускает `rollback` и проверяет результат.

## Проверка доставки

Для текущей сборки MkDocs в preview `mkdocs-check` проверены две публикации, отказ до переключения и откат. Версия `mkdocs-20261009-v2` осталась активной после `interrupt` (код 42); `rollback` вернул `mkdocs-20261009-v1`. Все HTTP-проверки прошли.
Операция `interrupt` намеренно завершает job ошибкой после загрузки файлов;
действующий релиз должен остаться прежним. Операция `rollback` меняет ссылку
на предыдущую версию, после чего выполняется тот же healthcheck.

Для отката нужны две успешно опубликованные версии. Старые релизы автоматически
не удаляются: политика хранения и очистка остаются отдельной задачей.

## Сравнение площадок

| Критерий | GitHub Pages | Helios |
| --- | --- | --- |
| Доставка | Pages-артефакт и API публикации | SSH/rsync и переключение ссылки |
| Контроль | Логи Actions и healthcheck | Логи Actions, SSH-осмотр каталогов и healthcheck |
| Откат в этом проекте | Повторная публикация нужного коммита | Переключение на сохранённую предыдущую сборку |
| Отказ при передаче | Публикацией артефакта управляет Pages | Частичная загрузка не активируется; проверено прерыванием rsync |
| Обслуживание | Не нужно администрировать веб-сервер | Нужно следить за ключом, свободным местом и сохранёнными релизами |

Время публикации зависит от размера сборки, сети и раннера. Единичный запуск
не позволяет оценить SLA или доказать преимущество одной площадки. Результаты
проверок текущей версии сохраняются локально вместе с материалами отчёта.

Замеры 9 октября 2026 года: публикация второй готовой сборки — **3,11 с**, откат с healthcheck — **1,02 с** (`/usr/bin/time -p`, локальный запуск тех же Bash-скриптов). Это не время всей CI-сборки.
