## Цель и методика

Нужно выбрать инструменты для сборки статического сайта MkDocs и публикации результатов исследований. Сравниваются три CI/CD-платформы — GitVerse, SourceCraft и GitFlic — и три места размещения: Helios ИТМО, Yandex Object Storage и Selectel S3.

Основа сравнения — официальная документация и текущий [workflow проекта](https://github.com/ansshour/practice-1-python/blob/main/.github/workflows/pages.yml). Сборка и публикация на GitHub уже проверены. Запуски на трёх сравниваемых CI/CD-платформах и деплой на отечественные хостинги в рамках T3 **не выполнялись**. Оценки миграции ниже являются инженерными оценками, а не измерениями.

Приоритеты для этого проекта: сохранить воспроизводимую сборку, обойтись без собственного раннера, передавать файлы на Helios по SSH и сохранить проверку результата публикации. Наличие собственного домена оценивается у хостинга: CI/CD-сервис сам по себе не определяет домен сайта.

## Сравнение CI/CD

### Выполнение и совместимость

| Критерий | GitVerse | SourceCraft | GitFlic |
| --- | --- | --- | --- |
| Модель раннеров | Облачные и self-hosted; есть раннеры организации | Облачные и self-hosted workers | Подключаемые агенты; документированы Shell, PowerShell и Docker. Доступность общего облачного агента для нового бесплатного аккаунта не подтверждена |
| Конфигурация | `.gitverse/workflows/*.yml`; `on`, `jobs`, `steps`, `uses`, `run` | `.sourcecraft/ci.yaml`; `workflows`, `tasks`, `cubes` | `gitflic-ci.yaml`; `stages`, задачи и `script` |
| Близость к GitHub Actions | Похожая структура; нужно проверить контексты, actions и сервисные API | Actions вызываются через `action` и `with` внутри кубика; это не перенос всего YAML без изменений | Прямой перенос `uses` не предполагается; команды переносятся в `script` |
| Близость к GitLab CI | Не является основным форматом | Есть отдельная интеграция пайплайнов GitLab, как и Actions — только на облачных воркерах | Похожая модель стадий и задач; совпадение отдельных ключей не доказывает полную совместимость |
| Готовые действия | Документированы actions, включая кэш и артефакты | GitHub Marketplace и переиспользуемые кубики/процессы | Каталог версионируемых CI/CD-компонентов и шаблоны |

Источники: [раннеры GitVerse](https://gitverse.ru/docs/cicd/docs/runners/), [синтаксис GitVerse](https://gitverse.ru/docs/cicd/docs/workflow), [концепции SourceCraft](https://sourcecraft.dev/portal/docs/ru/sourcecraft/concepts/ci-cd), [интеграция SourceCraft с Actions](https://sourcecraft.dev/portal/docs/ru/sourcecraft/concepts/gh-actions), [self-hosted SourceCraft](https://sourcecraft.dev/portal/docs/en/sourcecraft/tutorials/self-hosted-worker-sourcecraft), [конвейер GitFlic](https://docs.gitflic.ru/latest/en/cicd/pipeline/), [типы агентов GitFlic](https://docs.gitflic.ru/latest/setup/runner/agent_types/), [компоненты GitFlic](https://docs.gitflic.ru/latest/en/cicd/components/).

### Секреты, артефакты и кэш

| Критерий | GitVerse | SourceCraft | GitFlic |
| --- | --- | --- | --- |
| Секреты | Контекст `secrets`, в том числе передача в переиспользуемый workflow | Секреты репозитория; интеграция с Yandex Lockbox и сервисные подключения | Переменные CI/CD с признаком маскирования в логах |
| Артефакты | Сохранение файлов, передача между job и скачивание; по умолчанию 30 дней | Артефакты кубиков доступны для скачивания 14 дней | `artifacts` в конфигурации; скачивание через интерфейс и API |
| Кэш | Документирован `actions/cache`; конкретную версию нужно сверять с раннером | Перенос нашего `setup-uv` с `enable-cache: true` требует проверки; равноценный механизм в изученных материалах не подтверждён | Локальный кэш на агенте; распределённый кэш через S3 |
| Последствие для проекта | Можно сохранить общую структуру build/deploy | Нужно отдельно проверить кэш и переписать структуру задач | Потребуются настройка агента и правила хранения кэша |

Источники: [секреты в синтаксисе GitVerse](https://gitverse.ru/docs/cicd/docs/workflow), [артефакты GitVerse](https://gitverse.ru/docs/cicd/manuals/artifacts/), [кэш GitVerse](https://gitverse.ru/docs/cicd/manuals/caching/), [секреты SourceCraft](https://vibe.sourcecraft.dev/portal/docs/ru/sourcecraft/operations/secrets), [артефакты кубиков SourceCraft](https://sourcecraft.dev/portal/docs/ru/sourcecraft/concepts/ci-cd), [API переменных и артефактов GitFlic](https://docs.gitflic.ru/latest/en/api/cicd/), [кэш GitFlic](https://docs.gitflic.ru/latest/cicd/cache/).

Маскирование не заменяет ограничение прав: deploy-ключ должен давать доступ только к нужной области публикации. Проверка маскирования реальным запуском на этих платформах пока не проводилась.

### Бесплатные условия и доступность

| Критерий | GitVerse | SourceCraft Free | GitFlic |
| --- | --- | --- | --- |
| Облачное CI-время | 1000 минут/месяц для публичных и 500 для приватных репозиториев обычного пользователя/организации | 1000 минут/месяц для публичных и 1000 для приватных репозиториев на организацию | Подтверждённого общего лимита бесплатных облачных минут в изученных источниках нет |
| Ограничения | Облачная job — до 30 минут; артефакты — 500 МБ на все репозитории | До 5 параллельных CI-процессов; хранилище без LFS — 2 ГБ для каждой категории репозиториев | Команда до 5 человек бесплатна; это не обещание бесплатных вычислительных ресурсов |
| Self-hosted | Ресурсы и обслуживание своей машины | Не расходует квоту общего CI-времени; машину обслуживает владелец | Нужно учитывать стоимость и обслуживание агента |
| Доступность для учебной работы | Есть публичная документация и облачные раннеры; конкретный аккаунт не проверен | Есть бесплатная подписка; конкретный аккаунт не проверен | Есть бесплатная работа небольшой команды; условия агента нужно уточнить |

Источники: [лимиты GitVerse](https://gitverse.ru/docs/cicd/docs/limits/), [месячные квоты облачных раннеров](https://gitverse.ru/docs/cicd/docs/runners/cloud-hosted/), [тарифы SourceCraft](https://sourcecraft.dev/portal/docs/ru/sourcecraft/pricing), [правила GitFlic](https://docs.gitflic.ru/latest/company/billing_for_company/).

С 1 октября 2026 года SourceCraft изменил подписки. Для таблицы использована русская страница с новыми условиями; найденная английская версия ещё описывает Free/Pro. Платные AI-возможности не нужны для сборки этого сайта. Квоты следует повторно проверить перед миграцией, а отсутствие найденного лимита не считать отсутствием ограничений.

### Оценка документации

Это оценка удобства источников для данной работы, а не рейтинг качества сервисов:

- **GitVerse:** отдельные инструкции по раннерам, кэшу, артефактам и лимитам удобны для переноса небольшого Actions-проекта. Версии actions из примеров всё равно требуют проверки.
- **SourceCraft:** есть инструкции по GitHub Actions и self-hosted workers; ограничение интеграций облачными воркерами сформулировано явно. Обнаружено расхождение языковых версий тарификации.
- **GitFlic:** подробно описаны YAML, компоненты, агенты и распределённый кэш. Нужно различать возможности редакций и доступность ресурсов публичного сервиса.

Доступность документации не доказывает uptime платформы. Мониторинг доступности и сравнение надёжности CI-сервисов не проводились.

## Сравнение хостингов

| Критерий | Helios ИТМО | Yandex Object Storage | Selectel S3 |
| --- | --- | --- | --- |
| Модель | Учебный сервер с выданным аккаунтом | Бакет в режиме статического сайта | Публичный S3-бакет с включённым хостингом |
| Доставка файлов | Для P4 предусмотрены SSH и rsync; наличие rsync и права аккаунта ещё нужно проверить | S3-совместимый API и инструменты загрузки | S3 API, Swift API, панель и S3-инструменты |
| Собственный домен | Возможность не подтверждена; зависит от администрирования сервера | Поддерживается: имя бакета соответствует домену, нужна настройка DNS | Поддерживается пользовательский домен бакета |
| HTTPS | Публичный URL и действующий сертификат аккаунта ещё не проверены | Поддерживается; для своего домена настраивается сертификат, в том числе через Certificate Manager | Для пользовательского домена добавляется TLS-сертификат; его обновление нужно обслуживать |
| Оплата | Аккаунт у студента есть; текущие квоты и условия учебного доступа не проверены | Оплачиваются хранение, операции и трафик сверх бесплатного объёма | Pay-as-you-go: хранение, API-запросы и исходящий трафик; списания каждый час |
| Бесплатный объём | Публичный тариф и гарантированная квота не найдены | Стандартный класс: 1 ГБ хранения, 10 000 PUT/POST/PATCH/LIST и 100 000 GET/HEAD/OPTIONS в месяц; первые 100 ГБ исходящего трафика не тарифицируются | Постоянный бесплатный объём в изученной странице оплаты не заявлен; бонусы не приравниваются к бесплатному тарифу |
| Доступ и документация | Нужен учебный аккаунт. Открытые инструкции ИТМО есть, часть материалов старая | Нужны облачный аккаунт, права на бакет и платёжные условия; документация разделяет хостинг, HTTPS и оплату | Нужны аккаунт и баланс; есть отдельные инструкции по хостингу, сертификатам и оплате |

Источники по Helios: [учебная информация ИТМО об SSH-доступе](https://se.ifmo.ru/~ninomt/info.html) и условия P4 в задании. Эта инструкция не считается подтверждением актуального порта или URL конкретного аккаунта.

Источники по Yandex Cloud: [статический хостинг](https://yandex.cloud/ru/docs/storage/concepts/hosting), [свой домен и HTTPS](https://yandex.cloud/ru/docs/storage/operations/hosting/own-domain), [тарификация](https://yandex.cloud/ru/docs/storage/pricing).

Источники по Selectel: [хостинг](https://docs.selectel.ru/en/s3/buckets/website/), [загрузка объектов](https://docs.selectel.ru/s3/objects/upload-object/), [TLS-сертификаты](https://docs.selectel.ru/s3/manage/tls-ssl-certificates/), [оплата](https://docs.selectel.ru/s3/about/payment/).

### Что это означает для P4

Helios соответствует выбранному способу доставки по SSH/rsync. Для него планируются каталоги версий, preview веток и откат. Возможность переключения версии символьной ссылкой необходимо проверить на сервере — сейчас это проектное решение, не выполненная настройка.

Оба объектных хранилища подходят для статических файлов, но загрузка по S3 API не является SSH-деплоем. Чтобы буквально выполнить выбранное P4, нельзя незаметно заменить rsync загрузкой в бакет. Потребуется согласование другого способа или выбор сервера с SSH.

Предполагаемое преимущество S3 — отсутствие необходимости обслуживать веб-сервер. Ограничение для нашего сценария: обновление набора объектов не даёт атомарного переключения всего сайта само по себе. Версионирование отдельных объектов, например [в Selectel](https://docs.selectel.ru/s3/buckets/versioning/), также не заменяет согласованный откат HTML, CSS и JavaScript к одной сборке. Это вывод об архитектуре доставки, а не результат тестирования провайдера.

`git push` запускает CI, но не доставляет HTML в любой произвольный хостинг автоматически. Для рассматриваемого варианта Helios выбран SSH; для бакетов — S3 API. FTP и WebDAV не используются, их наличие у этих площадок не предполагается.

## Перенос нашего GitHub Actions workflow

Для подробного разбора выбран **GitVerse**: у него ближе структура workflow и есть облачные раннеры. Это рекомендация по документации; перенесённый workflow ещё не запускался.

Исходный файл — `.github/workflows/pages.yml`: получение исходников, установка Python из `.python-version`, `uv sync --locked`, сборка MkDocs, загрузка Pages-артефакта, публикация из `main` и HTTP-проверка.

| Элемент проекта | Что переносится | Что меняется для GitVerse + Helios |
| --- | --- | --- |
| Исходники сайта | Markdown, CSS, конфигурация MkDocs | Только адрес и базовый путь целевого сайта |
| Зависимости | `pyproject.toml`, `uv.lock`, `.python-version`, команда `uv sync --locked` | Проверить наличие Python 3.14.7 и uv 0.12.24 в среде раннера |
| Сборка | `uv run --frozen mkdocs build --strict`, каталог `dist/`, проверка битых ссылок | Задать полный `SITE_URL` с подкаталогом |
| Файл workflow | Общая модель `jobs` и `steps`, последовательность сборки | Перенести в `.gitverse/workflows/`; проверить триггеры и контекст `gitverse` вместо `github` |
| Checkout и setup-uv | Назначение шагов сохраняется | Проверить разрешение имени action, выбранный SHA и работу с репозиторием GitVerse; совместимость не следует только из одинакового имени |
| Кэш uv | Идея ключа по ОС и lock-файлу | Проверить встроенный кэш setup-uv либо описать отдельный `actions/cache` по инструкции GitVerse |
| Артефакты | Сохраняется необходимость передать `dist/` в deploy-job | Pages-артефакт заменить обычным артефактом платформы; проверить совместимые версии upload/download |
| Правило публикации | Только `main`, без deploy для pull request | Переписать выражение условия под контексты GitVerse; preview веток добавить отдельно в P4 |
| GitHub Pages | Содержимое `dist/` остаётся пригодным для статического хостинга | `deploy-pages`, `pages: write`, GitHub OIDC и environment `github-pages` не являются способом деплоя на Helios и удаляются |
| Доставка на Helios | — | Добавить SSH-ключ из секретов, проверенный `known_hosts`, rsync, переключение версии и откат |
| Healthcheck | Проверка HTTP 200 и контрольной строки | Заменить `page_url` из deploy-pages на URL Helios; учитывать путь preview |
| README | Описание сборки | Заменить ссылки и бейдж CI |

Документальные основания: [workflow GitVerse](https://gitverse.ru/docs/cicd/docs/workflow), [кэш](https://gitverse.ru/docs/cicd/manuals/caching/), [артефакты](https://gitverse.ru/docs/cicd/manuals/artifacts/), [механизм GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

Непереносима без замены именно интеграция публикации GitHub Pages. Это не утверждение, что из другого CI невозможно вызвать GitHub API с отдельной авторизацией: такой вариант означал бы сохранение зависимости от GitHub и выходит за выбранный маршрут на Helios.

### Оценка трудозатрат

Оценка для одного исполнителя, знакомого с YAML и SSH, при готовых аккаунтах и рабочих доступах. Время ожидания активации, поддержки и устранения сетевых ограничений не включено.

| Работа для GitVerse + Helios | Оценка, ч |
| --- | ---: |
| Перенос структуры YAML, событий и контекстов | 1–2 |
| Проверка Python и uv, actions, кэша и артефактов | 1–3 |
| SSH-доставка, секреты, known_hosts и healthcheck | 2–4 |
| Проверки основного и preview-путей, отказа доставки и отката | 2–4 |
| Всего | 6–13 |

Для SourceCraft нужно дополнительно перевести job/steps в tasks/cubes и проверить совместимость каждого action; ориентир на всю миграцию — **8–16 часов**. Для GitFlic добавляется настройка агента и перенос шагов в его YAML; ориентир — **8–18 часов**. Эти диапазоны не являются замерами или гарантированными сроками. Готовый агент GitFlic либо существующие шаблоны SourceCraft могут существенно сократить работу.

## Вывод

Для потенциального переноса этого небольшого проекта на отечественный CI/CD выбран **GitVerse**: его структура ближе к уже написанному workflow, а облачный раннер позволяет начать без администрирования отдельной машины. Для практического задания сохраняется **Helios**, потому что нужен SSH/rsync и учебный аккаунт уже есть. В P4 проверены доступ, основной и preview-пути, HTTPS и доставка на сервер. При смене CI доступ из нового раннера потребуется проверить заново.

Если приоритетом станет интеграция с сервисами Yandex Cloud, стоит выбрать SourceCraft и Object Storage, отдельно согласовав отличие от SSH-сценария P4. При необходимости управлять собственными агентами и использовать модель стадий GitLab разумно рассмотреть GitFlic. Если нужен статический хостинг без учебного аккаунта и есть бюджет на ресурсы, альтернативой служит Selectel S3.

Работающий GitHub Actions пока остаётся CI этого проекта. T3 обосновывает возможный выбор и объём миграции; создание аккаунтов, перенос CI и покупка ресурсов в рамках исследования не выполнялись.
